# Task B2-016-017 Fix 1 Handoff: Review of Claude Unit Test Failures

### Item 1a: `src/core/3d/transform/__tests__/gizmo.test.ts` — hitGizmo X-axis ray hit
1. Decision: Code is wrong.
2. Maths: Ray `(5/6, 0, -5) + t*(0, 0, 1)` intersects the X arrow shaft at `t = 5`, but `rayToSegmentDistance` inverted Cramer's signs giving `rayT = -5` (rejected by `rayT >= 0`), while plane bounds checked `u, v >= 0` instead of `u, v >= handle.length`, catching the ray at `v = 0` as `translate-xy`.
3. Fix: In `rayToSegmentDistance`, set `s = (a*e - b*d)/denom` and `t = (b*e - c*d)/denom`; in `hitGizmo`, restrict plane bounds to `u, v >= handle.length` and prioritize axis arrow hits over plane square hits when hit distances are within tolerance.

### Item 1b: `src/core/3d/transform/__tests__/gizmo.test.ts` — dragGizmo pure 1D translation
1. Decision: Code is wrong.
2. Maths: RayStart `(1, 0, -5)` and RayNow `(3.5, 0, -5)` intersect the X axis line at `x = 1.0` and `x = 3.5` expecting translation `+2.5`, but `closestPointOnLineFromRay` used negated formula `(b*d - a*e)/denom`, returning `-1.0` and `-3.5` and giving `deltaT = -3.5 - (-1.0) = -2.5`.
3. Fix: In `src/core/3d/transform/gizmo.ts` line 591, change `return (b * d - a * e) / denom;` to `return (a * e - b * d) / denom;` so `deltaT` evaluates to `+2.5`.

### Item 1c: `src/core/3d/transform/__tests__/gizmo.test.ts` — dragGizmo axis-aligned scale factor
1. Decision: Code is wrong (caused by the sign error in 1b).
2. Maths: RayNow at `x = xScale.length` yields `t1 = -length` via `closestPointOnLineFromRay`, producing `deltaT = -length` and `1 + deltaT/len = 0.0`, which clamps to `Math.max(0.0, 0.001) = 0.001` instead of expected `1 + len/len = 2.0`.
3. Fix: Correcting line 591 in `closestPointOnLineFromRay` to `(a * e - b * d) / denom` evaluates `deltaT = +length` and produces `scale[0] = Math.max(1 + len/len, 0.001) = 2.0` without altering the scale formula or clamp.

### Item 2: `src/core/3d/snap/__tests__/orientation.test.ts` — orientation 'normal' aligns matrix Z column with [1, 0, 0]
1. Decision: Code is wrong.
2. Maths: For `n = [1, 0, 0]`, `orientation.ts` chooses `guide = [0, 0, 1]` and computes `X = guide x n = [0, 1, 0]` and `Y = n x X = [0, 0, 1]`, swapping Y and Z into columns 0 and 1; the test expects standard orthonormal basis `X = [0, 0, -1]` and `Y = [0, 1, 0]` formed using world up `guide = [0, 1, 0]`.
3. Fix: In `orientation.ts`, use helper `guide = [0, 1, 0]` when `|n[1]| < 0.9` (falling back to `[0, 0, 1]` only when `n` is parallel to Y), computing `X = normalize(cross(guide, n))` and `Y = cross(n, X)` so columns are X=`[0, 0, -1]`, Y=`[0, 1, 0]`, Z=`[1, 0, 0]`.

### Item 3: `src/core/3d/snap/__tests__/snap.test.ts` — alignToNormal upside-down surface [0, 0, -1] (Case 16)

3. Fix: Update test Case 16 to assert `transformDirection(q, u) == n` (or allow `|q[0]| + |q[1]| == 1.0`), or update `alignToNormal` in `snap.ts` to choose `ortho = [1, 0, 0]` when `u` is along Z to satisfy the test's arbitrary preference.
