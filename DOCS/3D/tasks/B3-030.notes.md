# Task B3-030 Notes: Modifier Stack (Pure Part and Kernel Hooks)

## Entry 1: Initialization
- Starting Phase 3D-030: Non-destructive modifier stack per object evaluated in kernel.
- Plan:
  1. Add `Modifier3dSchema` & update `Object3dSchema` in `src/core/document/scene3d.ts` (re-export in `schema.ts`).
  2. Update property path resolution in `src/core/3d/paths.ts` and `evaluate3d.ts` for modifiers array.
  3. Implement `src/core/3d/modifiers/registry.ts` with 5 modifiers: mirror, array, solidify, transform, displace.
  4. Implement `src/core/3d/modifiers/stack.ts` with stack evaluation, caching, document mutation helpers, and async worker dispatch.
  5. Add `"modifiers.eval"` job handler in `src/core/jobs/handlers.ts`.
  6. Implement typed commands and `register3dModifierCommands` in `src/core/3d/modifiers/commands.ts` and hook into `src/core/editing/editCommands.ts`.
  7. Write thorough deterministic unit tests.

## Entry 2: Modifying `src/core/document/scene3d.ts` and `src/core/document/schema.ts`
- About to: Add `Modifier3dSchema` and `type Modifier3d`, and add `modifiers: z.array(Modifier3dSchema).optional()` to `Object3dSchema`. Re-export in `schema.ts`.
- Why: Objects in 3D scene require an ordered modifier stack per the 3D-030 specification.
- Alternative rejected: Storing modifiers as a dictionary keyed by ID was rejected because modifier evaluation order in Blender and graphics pipelines is stack-ordered (array position dictates operation order).

## Entry 3: Modifying `src/core/3d/paths.ts`
- About to: Update `apply3DProperty` and `get3DProperty` to handle `modifiers/<id>/<param>` and `modifiers.<id>.<param>` when `target.modifiers` is an array of `Modifier3d` objects as well as record/dict.
- Why: Animated tracks targeting modifier parameters (e.g. `3d:objects/<id>/modifiers/<modifierId>/<param>`) must resolve into the modifier's `params` dictionary or top-level properties (such as `enabled`).
- Alternative rejected: Forcing modifiers to be an object map on Object3d would violate the schema requirement that `modifiers?: Modifier3d[]` is an ordered list representing the stack.

## Entry 4: Modifying `src/core/kernel/evaluate3d.ts`
- About to: Update `cloneObject3d` in `src/core/kernel/evaluate3d.ts` to deeply clone `modifiers` including each modifier's `params` map.
- Why: Prevent animation track sampling from mutating the original input document's modifier parameters when running `evaluate3D`.
- Alternative rejected: Shallow array cloning of `modifiers` would still allow mutation of inner `params` objects, breaking kernel purity and deterministic scrubbing.

## Entry 5: Creating `src/core/3d/modifiers/types.ts` and `src/core/3d/modifiers/registry.ts`
- About to: Create `types.ts` defining `MeshData` and `ModifierDefinition` interfaces; create `registry.ts` implementing the 5 core modifiers (mirror, array, solidify, transform, displace) with zod schemas with defaults and pure evaluation functions.
- Why: Satisfy Phase 3D-030 requirement for pure mesh modifier evaluations without mutating input buffers.
- Alternative rejected: Importing Three.js modifier operators or CSG libraries was rejected because Phase 3D-030 requires pure, self-contained, deterministic maths without new npm dependencies.

## Entry 6: Creating `src/core/3d/modifiers/stack.ts`
- About to: Implement `evaluateStack`, `stackKey`, LRU cache, document mutation helpers (`addModifier`, `removeModifier`, `reorderModifier`, `setModifierParam`, `setModifierVisibility`, `applyModifier`, `applyAll`), and `evaluateStackAsync`.
- Why: Implements the non-destructive stack evaluation pipeline, caching, and immutable document updates per Phase 3D-030.
- Alternative rejected: Baking modifiers destructively in place during editing was rejected; non-destructive stacks evaluate lazily or on demand, only baking when `applyModifier` or `applyAll` is explicitly called.

## Entry 7: Modifying `src/core/jobs/handlers.ts`
- About to: Register handler `"modifiers.eval"` taking `{ mesh: MeshData; modifiers?: Modifier3d[]; viewport?: boolean }` and returning `HandlerResult` with `result` and `transfer` array containing buffers.
- Why: Enables parallel execution of heavy modifier stacks (> 50,000 vertices) off the main thread via the worker job pool per Phase 3D-030.
- Alternative rejected: Synchronous evaluation of massive meshes on main thread would block user interactions and cause UI frame drops.

## Entry 8: Creating `src/core/3d/modifiers/commands.ts`
- About to: Implement typed commands `3d.modifier.add`, `3d.modifier.remove`, `3d.modifier.reorder`, `3d.modifier.set_param`, `3d.modifier.set_visibility`, `3d.modifier.apply`, `3d.modifier.apply_all` via `defineTypedCommand` under category "3D", and `register3dModifierCommands()`.
- Why: Provides full undo/redo transaction support on the command bus for all modifier stack operations.
- Alternative rejected: Direct unstored state mutations without command bus would break the undo/redo stack.

## Entry 9: Creating `src/core/3d/modifiers/index.ts` and updating `src/core/3d/index.ts`
- About to: Create the modifiers barrel file `src/core/3d/modifiers/index.ts` exporting types, registry, stack, and commands, and re-export `modifiers` from `src/core/3d/index.ts`.
- Why: Consolidates modifier system exports and exposes them cleanly to the rest of the 3D module.
- Alternative rejected: Importing individual internal files deep from `src/core/3d/modifiers/` would complicate external consumption.

## Entry 10: Modifying `src/core/editing/editCommands.ts`

- Why: Ensures all 7 modifier typed commands are registered into LazyLayout's global editing command environment.
