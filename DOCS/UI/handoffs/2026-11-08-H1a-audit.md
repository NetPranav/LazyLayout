## Item 1: Toolbar mode switch (Design <-> Motion, Design <-> Code)

### Findings & Differences
1. **P Behavior:**
   - In P, `#tools` contains all mode tools in the DOM simultaneously. Design tools are direct children of `#tools`, Motion tools are inside `.mtools`, and Code tools are inside `.ctools`.
   - `.app[data-mode=motion]` and `.app[data-mode=code]` hide/show relevant tool clusters via CSS (`#tools>:not(.mtools):not(.tbghost){display:none}`).
   - During `onMode()`:
     - Old visible buttons are snapshotted and cloned into `.tbghost` which fades out and blurs (130ms, delay `i * 10ms`).
     - `#tools` width springs from `w0` (previous mode width) to `w1` (new mode natural width) using preset `B().shape`.
     - New mode buttons pop in with blur and scale (`scale .6 -> 1, blur 4px -> 0px`) staggered (`60ms + i * 14ms`).
     - Previous popovers are closed immediately (`closePop()`), any ongoing width animation is killed (`kill()`), and narrow lift state is evaluated.
2. **App Issue:**
   - In `Toolbar.tsx`, mode tools were conditionally rendered via JSX `{mode === "design" && ...}`.
   - When switching modes rapidly or via keyboard/mode tabs, `useLayoutEffect` tried to snapshot leaves, but in React DOM the previous mode was already unmounted. `snapKidsRef.current` was updated only on a delayed 700ms timer (`setTimeout(snapLeaves, 700)`). If the user switched modes within 700ms (e.g. Motion -> Design or Code -> Design), `snapKidsRef` was stale or contained the wrong mode's buttons.
   - The width animation `wAnim` was queued in `defaultHost.register` without synchronizing `bar.style.width`, causing Code mode to retain an artificial 330.68px width instead of its natural ~200px width.
   - Any open popovers (Shape, Easing, Export) were handled via React `setState`, which could conflict or leave open popover state during mode transitions.
   - Active tool state was not cleanly synchronized between modes (e.g. Select (V) / Hand (H) synchronization).

## Item 4: Insert box (+) fixed size & tab switching

### Findings & Differences
1. **Computed Dumps Comparison:**

| Property | P (`.ins`) | App (`.ll-ins`) | Status |
|---|---|---|---|
| Width | 520.47px / 520px | 519.39px / 520px | Matches within 1px |
| Height on Open | 400.36px / 400px | 399.53px / 400px | Matches within 1px |
| Height after tab switch | **400px fixed** in all tabs | **Shrank or grew** depending on content | **FAIL in App**: `.ll-ins` lacked fixed CSS height |
| Category sidebar (`.insl`) | width: 136px, overflow: auto | width: 136px, overflow: auto | Matches |
| Content panel (`.insr`) | flex: 1, overflow: auto, padding: 16px | flex: 1, overflow: auto, padding: 16px | Matches |

2. **Root Cause:**
   - In P, `.ins` has CSS `width: 520px; height: 400px; display: flex; flex-direction: column; overflow: hidden;`.
   - In the App, width and height were only set in inline `style={{ ... }}`.
   - When `surf` opened the box, `measure()` cleared inline `style.height = ""`. When `surf.end()` finished, `style.height` remained empty.
   - Without fixed CSS height on `.ll-ins`, switching tabs (e.g. from Sections with many cards to Basics, Fonts, or Recent with few cards) caused the entire box to shrink or grow with its content.
   - **Fix:** Set `.ll-ins { width: var(--ll-size-insert-w, 520px); height: var(--ll-size-insert-h, 400px); }` in CSS, ensure `Surf` keeps fixed dimensions, and content scrolls internally inside `.ll-insr`.

## Item 5: Custom canvas cursor activation & visibility

### Findings & Differences
1. **Observed Behavior:**
   - On page load, cursor did not activate on moving over canvas until a click occurred.
   - After opening and closing a context menu (or pressing Escape), the cursor was completely disabled and never reactivated on mouse move.
   - After opening and closing top-bar menus, cursor did not activate on mouse move over canvas.
2. **Root Cause:**
   - **Root Cause A (Suppression Check):** `CanvasCursor.tsx` had:
     ```tsx
     const hasActiveMenu = !!document.querySelector(
       ".menu.ll-open, .menu.open, [role=menu]:not([data-lv])"
     );
     ```
     `CanvasContextMenu` mounts a dormant submenu element into the DOM that matched `[role=menu]:not([data-lv])`. Once a menu was opened, this dormant submenu remained in the DOM, permanently disabling the cursor!
   - **Root Cause B (Scope Region):** `inRegion(t)` checked `viewport.contains(t)`. `viewport` was `.ll-stage-viewport` (inside `<Stage>`), which did NOT cover the background canvas (`[data-stage="canvas"]` / `.stagewrap`). Moving over the canvas background outside the artboard returned `false` for `inRegion`.
   - **Root Cause C (Cursor None Class):** In P, `#center.ll-on` applies `cursor: none !important` to `.stagewrap, .stagewrap *`. In the App, `ll-stage-cursor-active` was only added to `.ll-stage-viewport`, so the system cursor remained visible over the rest of the canvas.
   - **Root Cause D (Activation on Event):** When menus or popovers close, or after Escape, or on mode switch, no pointer event had fired, leaving the cursor hidden until a physical click.
   - **Fix:**
     - Fix `inRegion(t)` to check `.stagewrap, .ll-stagewrap, #center, [data-stage="canvas"]` (excluding floating panels, topbar, inspector).
     - Fix menu suppression to only check truly open, visible menus (`.ll-menu.ll-open, .menu.open, .ll-ctx.ll-open, .tbpop`).
     - Add listeners for `Escape`, window focus, menu close, mode switch, and initial pointer move to immediately wake and activate the cursor over the canvas without needing a click.
     - Ensure `#center.ll-on` hides system cursor over the entire canvas stage.
